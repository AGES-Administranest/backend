# ADR-14 — Modules for uploaded documents (purchase orders and NFSe)

**Status:**

- [ ] Accepted
- [ ] Rejected

**Context:** US-01 adds a second uploaded document, the NFSe (service invoice), next to the purchase order of US10. Everything the purchase order needs lives in `stock-entry` today: the file cycle (S3 key, presigned POST, upload check), the extraction run (claim, timeout, status), the review and the confirmation. The `extraction` module has one strategy, shaped like a purchase order. Copying that into a new module would duplicate the file cycle and the extraction run; moving it all into one shared "documents" module would make one module write to tables that belong to others, which ADR-01 forbids.

**Options:** (a) a new `service-invoices` module that copies what it needs from `stock-entry`; (b) a shared `documents` module that owns upload, extraction and the rows of both kinds; (c) a new `service-invoices` module, with the file cycle and the extraction run moved to places that hold no tables, and each module keeping the rows, statuses and errors of its own documents.

**Decision:** (c).

| Module | Holds | Writes to |
| --- | --- | --- |
| `infra/storage` (global) | `DocumentStorage` (S3 and the local emulator), `documentKey`, `UploadPolicy`, `DocumentUploads` (sign, verify, download URL) | the bucket only |
| `extraction` | `ExtractionService` (picks the strategy by document kind, applies its timeout), `runClaimedReading`, `core/` (PDF reading, text lines, Brazilian formats, tax ids), one folder per kind (`purchase-order/`, then `nfse/`) | nothing |
| `stock-entry` | `/stock-entries`, the purchase order upload policy, `PurchaseReadingService` (claim, supplier and item matching, save) | `purchase_invoice`, `purchase_invoice_line` |
| `service-invoices` (new) | `/service-invoices`, the NFSe upload policy, its reading, taker matching and duplicate warnings | `service_invoice` |
| `client`, `financial` | new methods only: taker lookup by tax id and by name; record, update and remove the income entry of a service invoice | their own tables |

Nothing imports `stock-entry` or `service-invoices`; the modules below them receive ids and values, never a document module.

- **Storage is not a module under `modules/`.** It has no route and no table, and `infra/storage` is already the global module that wraps S3. `DocumentUploads` returns a result (`stored`, `missing`, `mismatch`) and raises no domain error: each module turns it into its own codes (`INVOICE_*` stays as the app knows it, ADR-07).
- **File metadata stays in each table.** `file_name`, `file_hash`, `uploaded_at` and the extraction columns are repeated in `purchase_invoice` and `service_invoice` instead of a shared `document` table. Duplicate-file checks run per module.
- **Extraction stays synchronous** inside `POST /:id/uploaded`, with the statuses of ADR-05 and no queue: reading a text layer takes well under a second. This replaces the queue part of ADR-05. `runClaimedReading` keeps the guarantee a worker would give: only the request that claims the row reads it, a claim older than twice the timeout can be taken over, and a failure puts the row back to `PENDING`.
- **One strategy per document kind.** Each strategy has its own result type, failure reasons and settings (timeout, labels). Failures any document can have (`unreadable`, `unsupported_format`, `no_text_layer`, `timeout`) come from `core/`.
- **`extraction_job` is dropped**, with the `ExtractionJobStatus` enum. No code uses it, its foreign key points only to `purchase_invoice`, and the extraction is synchronous.
- **There is no `POST /service-invoices`.** As in US10, the draft is born in `POST /service-invoices/:id/upload-url` with an id generated by the app (ADR-09). With the offline mode out of US-01, there is no NFSe without a PDF.
- **The `/stock-entries` contract does not change**: routes, responses and error codes stay as the app uses them.

**Consequences:** (+) the NFSe reuses the file cycle and the extraction run without copying them; (+) each module still writes only to its own tables, which code review can check (ADR-01); (+) a new kind of document is a new strategy folder plus its owner module. (−) the file and extraction columns are repeated in two tables; (−) the claim, status and save steps are written once per owner module, though `runClaimedReading` keeps their order in one place; (−) the purchase order and NFSe flows can drift apart in details unless reviews compare them.
